## Step 3 — Inject %%RAW_MD%%

Read the full content of `WALKTHROUGH.md` and produce the value with:

```js
// CRITICAL: use String.fromCharCode(92) to get a literal backslash.
// Writing '<\\u003c' in Node.js source DOES NOT WORK — Node resolves \u003c to '<' at parse time.
const bslash = String.fromCharCode(92);
const RAW_MD = JSON.stringify(fs.readFileSync('WALKTHROUGH.md', 'utf8'))
  .replace(/<\/script>/gi, bslash + 'u003c/script>')
  .replace(/<script/gi, bslash + 'u003cscript');
```

**Why the `<script>` / `</script>` escapes are mandatory:** The HTML parser scans raw bytes for both `<script` and `</script>` — it does not care that the tag is inside a JavaScript string. Any walkthrough of a web project will likely contain HTML snippets with `<script src="..."></script>` tags (from showboat capturing real code). Without these escapes, the HTML parser will either open new script contexts (for `<script` tags) or close the existing `<script>` block prematurely (for `</script>` tags), splitting the application JS into broken fragments. The page will load with an empty content area and "Invalid or unexpected token" errors in the console — with no obvious indication of what went wrong.

**Why `String.fromCharCode(92)` instead of backslash literals:** Node.js resolves all escape sequences (`\u003c`, `\s`, `\\`) at string construction time — before `.replace()` ever runs. This means `'<\\script'` becomes `<script` (unchanged) and `'<\\u003cscript'` also becomes `<script`. The only way to get a literal `\u003c` into the output file is to build the backslash character at runtime with `String.fromCharCode(92)`. The browser's JS engine then sees `\u003c` in the JSON string and correctly resolves it to `<` when parsing.

**Also escape `<script>` in quiz option text:** If any quiz MC option or feedback mentions `<script>`, use `&lt;script&gt;` instead — the quiz HTML is injected outside of RAW_MD and doesn't go through the escaping pipeline.

The injection replaces `%%RAW_MD%%` exactly — the surrounding `var RAW_MD =` and `;` are already in the template.

## Step 5 — Inject %%CHAPTER_EXTRAS%%

This is the editorial callout layer. Write one callout per chapter using the `callout()` helper function already in the template.

### The callout function signature
```js
callout(type, icon, htmlString)
```
- `type`: `'insight'` (blue tint) or `'pattern'` (lighter blue tint)
- `icon`: emoji string
- `htmlString`: HTML content — use `<p>` tags, `<strong>`, `<code>`, etc.

### How to structure the injection
The `%%CHAPTER_EXTRAS%%` placeholder sits inside `getChapterExtras(idx)`. Write `if (idx === N)` blocks that set `post`:

```js
  if (idx === 0) {
    post = callout("insight", "💡", "<p>...</p>");
  }
  if (idx === 1) {
    post = callout("pattern", "🧩", "<p>...</p>");
  }
  // ... etc
```

**Always use the `co()` helper defined in the build script.** Pass the HTML content as a plain JS string — `JSON.stringify()` inside `co()` handles all escaping. Never construct callout strings by hand.

`pre` is almost never used — it injects content before the rendered markdown. Only use `pre` for a chapter where the opening needs replacing (rare).

### What makes a good callout — the quality bar

A callout earns its place by saying something the reader wouldn't have articulated themselves after reading the chapter.

**Bad callout (summary):** "This chapter covers the glossary.json data model and how it connects the three pipeline stages."
→ This just repeats what the chapter already said.

**Good callout (insight):** "glossary.json isn't just a data file — it's the handoff point between every phase of the system. extract-terms.js writes to it, the admin UI curates it, build.js consumes it. If you want to understand how the three stages connect, start here."
→ This names a structural insight the reader might have absorbed passively but not consciously noticed.

**Good callout (pattern):** "This is Defensive Parsing — treating LLM failure as a first-class case, not an edge case. Every function that touches model output validates before using. This pattern shows up in any serious LLM integration."
→ This names an abstract pattern, makes it transferable, and tells the reader what to call it.

### Callout type guide
- `'insight'` + `'💡'` — for payoff moments, architectural "why", zero-network-requests reveals, the thing that makes the system elegant
- `'pattern'` + `'🧩'` — for naming a recognizable design pattern that appears in this chapter and recurs in other codebases
- `'insight'` + `'⚡'` — for performance or tradeoff observations
- `'insight'` + `'🎯'` — for "the one thing to remember from this chapter"

### Special case: the closing chapter (Ch10 / mental model)
The final content chapter (the "mental model" or "how it all connects" chapter) should use `.callout-box` instead of `.callout`. Wrap the opening paragraph using a `rendered.replace()` call in `%%COMPACT_REPLACEMENTS%%`:

```js

    /(<p>FIRST SENTENCE OF OPENING PARA[\s\S]*?<\/p>)/,
```

## Step 6 — Inject %%COMPACT_REPLACEMENTS%%

This is the compact snippet layer. The function `applyCompactReplacements(idx, rendered)` already exists in the template — you just fill its body.

### When to compact a snippet

Look for code blocks where:
1. **Same schema repeated N≥3 times**: e.g. a JSON output showing 5 records with the same fields, varying only in values. Replace with 1 representative record.
2. **Same structure, N implementations**: e.g. the same function pattern shown for 3 different providers/platforms, full implementations side-by-side. Replace with a compact structural diff showing only what differs.

Do NOT compact blocks where:
- The length conveys complexity (a 40-line function that is genuinely doing 40 different things)
- The repetition is intentional and pedagogically useful

### How to write the replacement

```js
if (idx === N) {
  rendered = rendered.replace(
    /<div class="cb TYPE">[\s\S]*?UNIQUE_ANCHOR_STRING[\s\S]*?<\/pre><\/div>/,
    '<div class="cb NEWTYPE"><div class="cb-hdr"><span class="cb-dot"></span>LABEL<\/div><pre><code>COMPACT_CONTENT<\/code><\/pre><\/div>'
  );
}
```

The regex must:
- Start with `<div class="cb TYPE">` where TYPE is the original block type (`out`, `plain`, etc.)
- End with `<\/pre><\/div>` (the end of the pre block is a reliable anchor)
- Include a unique string in the middle to identify which specific block to replace (copy a distinctive phrase from the block content — box-drawing characters survive HTML escaping unchanged)

## Step 7 — Inject %%QUIZ_CORRECT%%, %%QUIZ_FEEDBACK%%, %%QUIZ_HTML%%

Generate a 10-question quiz. Three parts:

### Part A — %%QUIZ_CORRECT%%
A plain JS object: `{ q1:'B', q2:'A', q3:'C', q4:'B', q5:'B', q6:'B' }`
The correct letter (A/B/C/D) for each of the 6 multiple-choice questions.

### Part B — %%QUIZ_FEEDBACK%%
A JS object with feedback text per MC question:
```js
{
  q1: 'Explanation of why the correct answer is correct, written as new information...',
  q2: '...',
  ...
  q6: '...'
}
```

**Feedback quality rules — critical:**
- Do NOT start with "Correct." or "Incorrect." — the feedback is shown regardless of which answer was chosen
- Write it as new information that builds understanding, not as a verdict
- Each feedback block should: (1) name the mechanism, (2) explain why it works that way in one sentence, (3) optionally name the consequence
- Use `<code>` tags for function names, file names, field names
- Length: 2-4 sentences is ideal

**Example of bad feedback:**
> "Correct. The definition was embedded at build time."

**Example of good feedback:**
> "`build.js` reads every published term from `glossary.json` and injects the definition as a `data-nutshell` attribute on the span at compile time. By the time a reader opens the page, all definitions are already inside the HTML. Zero network requests on click."

### Part C — %%QUIZ_HTML%%
The return value of `buildQuizHTML()` — a JavaScript string expression using the `mc()` and `rv()` helpers.

**Critical: no leading newline.** The template uses `return (%%QUIZ_HTML%%);`. If `%%QUIZ_HTML%%` starts with a newline, JavaScript's Automatic Semicolon Insertion (ASI) treats the `return` as complete and the function returns `undefined` — the quiz shows as "undefined" with no other error. Always start `%%QUIZ_HTML%%` with the first expression, not a blank line.

### What makes a good quiz question — the quality bar

The quiz tests **gut-level intuition and systems thinking**, not fact recall. A reader who memorised bullet points should not automatically get all six right.

**For Tier 1 — Foundations:**
- Tests whether the reader understands the system's core architecture: what happens where, what depends on what
- Example question type: "Where does X come from when Y happens?" — requires understanding the data flow, not just knowing a fact
- The distractors must be plausible. A reader who read carelessly should be able to pick the wrong answer and believe it.

**For Tier 2 — Mechanics:**
- Tests whether the reader understands *why* specific implementation choices were made
- Example question type: "Why does X do Y instead of Z?" — requires understanding the tradeoff, not just the behavior
- Good Tier 2 questions often have a "performance" distractor, a "framework limitation" distractor, and a correct "design choice" answer

**For Tier 3 — Design Thinking:**
- Shows a real architectural scenario and asks what would happen, what you'd gain/lose, or what's actually required
- The "Think about it..." prompt gives the reader one specific lens to use
- The answer should model how to reason about the tradeoff, not just give the correct conclusion
- Reveal button is collapsible (already handled by `quizReveal()`) — reinforce this by not writing the answer as a lecture

**Score message brackets (already in template, but customize for the project):**
- 6/6: "Clean sweep. You understood the system, not just the facts."
- 4+: "Solid. Worth re-reading [specific chapter names from this project] if any mechanics felt shaky."
- 2+: "The big picture is there, but some implementation details are fuzzy."
- 0+: "Go back and re-read. These ideas often take a second pass to settle."

Customize the 4+ message to reference actual chapter names from the project being rendered.

## Step 8 — Write the output and VALIDATE

**Always write the file via a Node.js build script, not inline shell heredocs.** This avoids shell quoting hazards.

**Always use `safeReplace()` for all placeholder injections** — never use `String.replace()` directly. `String.replace()` treats certain `$` sequences in the replacement string as special (`$&` inserts the matched text, `$'` inserts the text after the match, etc.). The RAW_MD string is ~60-100KB of walkthrough content and will commonly contain `$` characters in shell commands, regex patterns, or template literals. These silently corrupt the output in ways that are very hard to debug.

```js
// REQUIRED: use this for every placeholder injection, no exceptions
function safeReplace(str, search, replacement) {
  const idx = str.indexOf(search);
  if (idx === -1) return str;
  return str.slice(0, idx) + replacement + str.slice(idx + search.length);
}

// Example usage — replace String.replace() with safeReplace() everywhere:
html = safeReplace(html, '%%RAW_MD%%', RAW_MD);
html = safeReplace(html, '%%PROJECT_NAME%%', PROJECT_NAME);
// ... etc for every placeholder
```

## Critical: JavaScript string quoting rules

**The only safe approach is `JSON.stringify()` for all prose content.**

The build script is a Node.js program. Node.js resolves Unicode escapes (`\u0027` → `'`) at string construction time — *before* the value is written to the HTML file. This means `\u0027` inside a Node.js template literal or string literal becomes a raw apostrophe in the output, which then breaks the JS in the browser.

**Do NOT use `\u0027`, `\'`, or any manual escape for apostrophes.** These approaches silently produce broken output. Use `JSON.stringify()` instead — it produces a correctly escaped string literal regardless of what apostrophes, quotes, or special characters appear in the content.

```js
  return 'mc(' + JSON.stringify(qid) + ', ' + JSON.stringify(qtext) + ', [' +
    opts.map(o => JSON.stringify(o)).join(', ') + '])';
}
function qrv(id, qtext, think, answer) {
  return 'rv(' + JSON.stringify(id) + ', ' + JSON.stringify(qtext) + ', ' +
    JSON.stringify(think) + ', ' + JSON.stringify(answer) + ')';
}
```

### QUIZ_FEEDBACK — build as an object, serialize with JSON.stringify

```js
const qfb = {
  q1: "Feedback text for q1...",
  q2: "Feedback text for q2...",
  // ... through q6
};
const QUIZ_FEEDBACK = '{\n' + Object.entries(qfb).map(([k,v]) => `  ${k}: ${JSON.stringify(v)}`).join(',\n') + '\n}';
```

### QUIZ_HTML — join parts with no leading newline

The template uses `return (%%QUIZ_HTML%%);`. If `%%QUIZ_HTML%%` starts with a newline, JavaScript's ASI treats the `return` as complete and the function returns `undefined`. Always start with the first expression:

```js
const quizParts = [
  JSON.stringify('<div class="quiz-tier-label">Tier 1</div>'),
  // ...
  qmc('q1', 'Question text?', ['Option A', 'Option B', 'Option C', 'Option D']),
  // ...
];
const QUIZ_HTML = quizParts.join(' +\n');  // NO leading newline
```

### CHAPTER_DEFS — use chap() helper, never write subtitles by hand

```js
const CHAPTER_DEFS = [
  chap('01', 'Chapter 1', 'Project Overview', 'One-sentence description of what this chapter covers.', '/^## 1\\./'),
  // ... one chap() call per chapter ...
  chap('\u2746', 'Quiz', 'Test Your Understanding', "The goal isn't to check if you memorised the walkthrough. It's to find out if you've built a real mental model of the system.", '/^$NOMATCH$/'),
].join(',\n');
```

Note: the quiz entry subtitle is written as a plain JS string here (inside the Node.js source), so apostrophes in it are fine — `JSON.stringify()` inside `chap()` handles the escaping when writing to the output file.
