You are going to take the completed `WALKTHROUGH.md` in the current working directory and render it into a polished, self-contained HTML reader.

Your job is to:
1. Read `WALKTHROUGH.md`
2. Generate a `walkthrough-config.json` file with project-specific content
3. Run `node ~/.claude/skills/walkthrough-render/build.js` which reads the config + template and produces `walkthrough-reader.html`

**Do NOT write a build script.** The build script is static and already exists. You only write the JSON config.

---

## Step 1 — Read and understand the walkthrough

Read `WALKTHROUGH.md` in full. Note:
- The project name (first H1 heading, after "Codebase Walkthrough: ")
- The number of chapters (count the `## N.` headings)
- The title and first substantive paragraph of each chapter
- Any code blocks that repeat the same structure multiple times

---

## Step 2 — Generate `walkthrough-config.json`

Write a file called `walkthrough-config.json` in the current working directory. The build script reads this file and handles all escaping, template injection, and validation automatically.

### Complete schema

```json
{
  "projectName": "string — short project name",
  "authorName": "string — author name for metadata row",

  "chapters": [
    {
      "num": "string — zero-padded ('01' through '10', then '\u2726' for quiz)",
      "label": "string — 'Chapter N' or 'Quiz'",
      "title": "string — chapter title from H2 heading",
      "subtitle": "string — one-sentence description of what the chapter covers"
    }
  ],

  "chapterExtras": [
    {
      "idx": "number — chapter index (0-based)",
      "type": "string — 'insight' or 'pattern'",
      "icon": "string — emoji",
      "html": "string — HTML content for callout body"
    }
  ],

  "closingChapterBox": {
    "chapterIdx": "number — index of closing chapter (usually 9)",
    "openingWords": "string — the first few distinctive words of the opening paragraph (plain text, no regex)",
    "projectName": "string — used in 'PROJECT in one paragraph:' label"
  },

  "compactReplacements": [
    {
      "chapterIdx": "number",
      "findPattern": "string — regex pattern to match the block to replace",
      "replacement": "string — HTML to replace with (no $1 support)"
    }
  ],

  "quiz": {
    "correct": { "q1": "A-D", "q2": "A-D", "q3": "A-D", "q4": "A-D", "q5": "A-D", "q6": "A-D" },
    "feedback": { "q1": "string (may contain HTML)", "...": "..." },
    "mc": [
      { "id": "q1", "question": "string", "options": ["Option A", "Option B", "Option C", "Option D"] }
    ],
    "rv": [
      { "id": "rv7", "question": "string", "think": "string", "answer": "string" }
    ]
  }
}
```

## Field-by-field guide

### projectName

Extract from the H1 heading of `WALKTHROUGH.md`. The H1 follows this pattern:
```
# Codebase Walkthrough: <PROJECT NAME> — <optional subtitle>
```
Take only the part between `Codebase Walkthrough: ` and the first ` —` or end of line.

If `` was passed to this skill, use that as the project name instead.

**Never use generic fallbacks like "Reading Assistant", "Project", or "Codebase".**

### authorName

The author's name. If the WALKTHROUGH.md was generated by showboat, the author line is in the metadata header. If you can't find a name, use the system username or ask the user.

### chapters

One entry per chapter in the walkthrough, plus a final quiz entry.

- `num`: zero-padded string (`"01"` through `"10"`, then `"\u2726"` for quiz)
- `label`: `"Chapter N"` for content chapters, `"Quiz"` for the last entry
- `title`: the chapter title as it appears after the number in the H2 heading
- `subtitle`: **specific, not generic**. Read the chapter's first paragraph. "Trace one term from raw Markdown to an animated popup." is better than "Covers data flow."

**Note:** `headingPattern` is auto-generated by build.js from the chapter number. You do NOT need to provide it.

The final entry must always be:
```json
{ "num": "\u2726", "label": "Quiz", "title": "Test Your Understanding", "subtitle": "The goal isn't to check if you memorised the walkthrough. It's to find out if you've built a real mental model of the system." }
```

### chapterExtras — editorial callouts

One callout per content chapter (idx 0 through 9). This is the editorial layer that makes the reader valuable.

**Callout type guide:**
- `"insight"` + `"💡"` — payoff moments, architectural "why", zero-network-requests reveals
- `"pattern"` + `"🧩"` — naming a recognizable design pattern that appears in this chapter
- `"insight"` + `"⚡"` — performance or tradeoff observations
- `"insight"` + `"🎯"` — "the one thing to remember from this chapter"

**What makes a good callout:**

A callout earns its place by saying something the reader wouldn't have articulated themselves.

**Bad (summary):** "This chapter covers the glossary.json data model and how it connects the three pipeline stages."
→ Just repeats what the chapter said.

**Good (insight):** "glossary.json isn't just a data file — it's the handoff point between every phase of the system. extract-terms.js writes to it, the admin UI curates it, build.js consumes it."
→ Names a structural insight the reader absorbed passively but didn't consciously notice.

**Good (pattern):** "This is Defensive Parsing — treating LLM failure as a first-class case, not an edge case. Every function that touches model output validates before using."
→ Names an abstract pattern, makes it transferable.

The `html` field is an HTML string. Use `<p>`, `<strong>`, `<code>` tags. Example:
```json
"html": "<p>This is <strong>Defensive Parsing</strong> — treating LLM failure as a first-class case.</p>"
```

### closingChapterBox

The final content chapter (usually "How it all connects") gets a special callout-box that wraps the opening paragraph. The build script handles all regex construction and the `$1` backreference — you just provide plain text:

- `chapterIdx`: the 0-based index (usually 9)
- `openingWords`: the first few distinctive words of the chapter's opening paragraph, as plain text. Example: `"Nutshell is a three-stage pipeline"`. The build script constructs the regex internally — you never write regex for this field.
- `projectName`: used in the label "PROJECT in one paragraph:"

**Important:** Use enough words to uniquely identify the paragraph. The first 5-8 words are usually sufficient. Target the paragraph that best **summarizes what the project does and why it exists** — not architecture or implementation details. Good examples: "Kirana Tap is, at its core, a translation engine..." or "Nutshell is a three-stage pipeline built around a JSON file..." Bad examples: paragraphs about architectural layers, design patterns, or implementation choices. The box should answer "what does this project do?" not "how is it built?"

**Also:** Make sure the paragraph you target is NOT redundant with the Chapter 10 chapterExtra callout (the "one sentence to remember" insight). They should complement each other, not repeat the same content.

### compactReplacements

Optional. Use when a code block has repetitive content that should be compacted:
- Same JSON schema repeated 3+ times → replace with 1 representative entry
- Same function pattern shown for 3+ providers → replace with a compact structural diff

Each entry has:
- `chapterIdx`: which chapter (0-based)
- `findPattern`: regex string to match the block (no delimiters). Use a distinctive anchor string from the block content. Box-drawing characters (`─`) survive HTML escaping and make reliable anchors.
- `replacement`: the compact HTML to replace with. **No `$1` support** — the entire matched block is replaced.

If no compacting is needed, use an empty array: `"compactReplacements": []`

### quiz

The quiz has three tiers. You provide the content; the build script handles all HTML structure, tier labels, and score box.

**quiz.correct** — Object mapping question IDs to correct letters:
```json
{ "q1": "B", "q2": "C", "q3": "A", "q4": "B", "q5": "C", "q6": "A" }
```

**quiz.feedback** — Object mapping question IDs to feedback text. May contain HTML (`<code>` tags, etc.).
- Do NOT start with "Correct." or "Incorrect." — feedback is shown regardless of answer
- Write as new information that builds understanding
- Name the mechanism, explain why, optionally name the consequence
- 2-4 sentences is ideal

**quiz.mc** — Array of exactly 6 multiple-choice questions. First 3 are Tier 1 (Foundations), last 3 are Tier 2 (Mechanics).

Each: `{ "id": "q1", "question": "...", "options": ["A", "B", "C", "D"] }`

**IMPORTANT:** If any quiz option text mentions `<script>`, you MUST use `&lt;script&gt;` instead. The quiz HTML is not processed by the script-tag escaping pipeline.

**Tier 1 — Foundations:** Tests core architecture — what happens where, what depends on what. Distractors must be plausible.

**Tier 2 — Mechanics:** Tests *why* specific implementation choices were made. Requires understanding the tradeoff, not just the behavior.

**quiz.rv** — Array of exactly 4 design-thinking scenarios (Tier 3). No scoring.

Each: `{ "id": "rv7", "question": "...", "think": "...", "answer": "..." }`
- `question`: a real architectural scenario
- `think`: one specific lens to reason with
- `answer`: models how to reason about the tradeoff, not just the conclusion

## Step 3 — Run the build

```bash
node ~/.claude/skills/walkthrough-render/build.js
```

The build script:
1. Reads `template.html` from the skill directory
2. Reads `WALKTHROUGH.md` from the current directory
3. Reads `walkthrough-config.json` from the current directory
4. Performs all placeholder injections with safe escaping
5. Writes `walkthrough-reader.html`
6. Validates: script tag count (must be exactly 2), JS syntax, no remaining placeholders
7. Opens the browser

If the build fails, read the error message and fix `walkthrough-config.json` accordingly.

---

## Important rules

- **Do NOT write a build script.** Only write `walkthrough-config.json`. The build logic is handled by the static `build.js`.
- Do not modify `WALKTHROUGH.md`. It is read-only input.
- Do not modify `template.html` or `build.js`.
- If `walkthrough-reader.html` already exists, confirm with the user before overwriting.
- The build script handles all `<script>` tag escaping in the walkthrough content automatically. You do NOT need to worry about this — except in quiz option text, where you must use `&lt;script&gt;`.
